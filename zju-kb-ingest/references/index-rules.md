# 00 INDEX｜浙大校园信息站｜v1.2

> 本规则适用于可信协作者和协作 AI。处理资料前先读本规则；拿不准时进入 `98 待分拣与待核验`。本规则是主库的唯一分类依据，不是面向学生的事实材料。

## 1. 收录范围与核心规则

收录目标：帮助学生获得稳定、可追溯的校园生活、学习与办事信息。

1. 一份资料只放一个主目录，不重复导入。
2. 按“它主要解决哪个学生问题”分类，而非按来源网站分类。
3. 只要对学生有用、来源说得清、能判断主题目录，就直接收录。官方资料、论坛帖和个人经验都可以收；在日志中标 `官方`、`经验` 或 `待处理`。
4. 不收录个人隐私、群聊原文、营销软文、违法或无法核验的材料。
5. 文件在本地生成规范命名副本后上传；网页保留源站标题，并在 `LOG 01` 留下原始链接与导入日期。
6. 成功新增资料后记 `LOG 01`；重要状态变化记 `LOG 02`；规则或目录变化记 `LOG 03`。日志只在“导入成功且目标目录可见”后追加。
7. 新子类只影响之后的新资料；禁止为了迁移而重复导入。
8. `98` 只收来源完全不明、无法判断目录、内容彼此矛盾或明显可能误导的资料；它不是“非官方资料区”。
9. `已导入` 只表示资料已进入知识库；只有后续实际检索/问答测试通过，才可标为“AI 检索已验证”。两者不得混写。

## 2. 标题与文件名

本地上传文件使用：

```text
{年份或核验日期}｜{主题}｜{适用范围}｜{官方/经验/待处理}.{原扩展名}
```

示例：

```text
2026｜本科生选课规则｜全校｜官方.pdf
2026-08 核验｜紫金港食堂与就餐建议｜紫金港｜经验.docx
待处理｜竞赛加分认定规则｜本科生｜待处理.pdf
```

网页没有可供 API 预先重命名的本地文件名，保持源网页标题；依靠正确目录和 `LOG 01` 保留其来源、状态与初始位置。

## 3. 状态

| 状态 | 使用情形 |
| --- | --- |
| 官方 | 学校、学院或职能部门的当前页面与文件 |
| 经验 | CC98、公开论坛、同学或个人的校园生活、学习与办事经验；有来源即可收录 |
| 待处理 | 来源完全不明、分类不清、相互矛盾或明显可能误导的资料 |
| 历史资料 | 明确过期但需要追溯的内容；不作为当前答案 |

高时效主题包括报到、校历、选课、考试、竞赛加分、奖助、评优、交通与食堂安排，尽量带年份或核验日期；暂时没有也可收录，但在日志留出来源与导入日期，之后发现失效再处理。

## 5. 从 0 到 1 的单条入库流程

1. **读 INDEX**：先看资料是否对学生有用、来源能否说清、能否选一个主题目录；三项都可以，就直接收录。
2. **看来源与时效**：标为 `官方`、`经验`、`待处理` 或 `历史资料`；高时效主题尽量写年份或核验日期。
3. **选唯一主目录**：按上表的“主要解决问题”放置；分类不清进 `98`。
4. **处理标题**：本地文件先做规范命名副本；网页保留来源网页标题；原生笔记第一行使用 `# 标题`。论坛和经验资料不因“不是官方”而改放 `98`。
5. **导入并核对**：网页导入须确认接口整体与逐条结果均成功；文件/笔记须确认写入成功。随后在目标目录翻页核对条目可见；失败不记成功日志。导入成功不等于 AI 已完成索引。
6. **追加日志**：新增资料写 `LOG 01`；后续审核、归档或移动写 `LOG 02`；规则/目录变化写 `LOG 03`。

## 6. 协作者整理 `98`

可信协作者均可处理 `98`：补来源、判断主目录，或发现它其实只是正常经验资料时直接归入对应主题目录；然后在 `LOG 02` 追加重要状态变化。无需审批流。若不能移动，不要重复导入；保留原条目，在 `LOG 02` 记下“待管理员客户端整理”。

## 7. 分类变更

仅在一个主题明显变多、经常被查找或现有目录已造成混乱时，增加二级目录。先更新 INDEX 与 `LOG 03`，之后的新资料按新位置收录；历史资料不要求全量迁移。

INDEX 采用前向、追加式维护：需要改规则时，优先在同一篇 `00 INDEX` 原生笔记末尾追加一个“生效补丁”，版本号递增；不要新建第二篇同名 INDEX。协作 AI 先读取正文，再以最高版本的生效补丁为准。每个补丁必须同步有一条 `LOG 03`。共享库里的 `00 INDEX` 永远是权威；本地 Skill 镜像仅用于 API 无法可靠读取共享笔记全文时的离线参考。发现版本不一致时应提示并尽快更新镜像，但不因镜像版本单独阻止一项已经获得管理员同意、且按共享 INDEX 分类的导入。

`00 INDEX` 由知识库管理员维护。官方笔记 API 只能追加当前账号自己创建的笔记，协作者不能经 API 直接改管理员创建的 INDEX；协作者提出规则变更时先写自己的 `LOG 03`，管理员再决定是否写入 INDEX 生效补丁。

## 8. 日志与编号规则

> 所有日志仅供知识库管理、审计与追溯；不得作为面向学生的事实依据或回答来源。每篇原生日志笔记都以标题第一行和本免责声明开头。

- 每位协作者维护自己的三条原生日志：`00 LOG 01｜资料登记｜{执行者}｜{简称}`、`00 LOG 02｜状态变更｜{执行者}｜{简称}`、`00 LOG 03｜规则变更｜{执行者}｜{简称}`。首次使用时由该协作者新建，放进手动建立的 `00 管理日志` 目录；之后只追加自己创建的那三条笔记。不得通过 API 追加其他人的日志。早期未带简称的日志作为历史兼容条目保留，不通过 API 改名。
- 首次使用 Skill 时，协作者必须主动填写两项身份：`日志显示名`（写入日志标题与执行者字段）和 `固定简称`（2–8 位英文/数字，写入资料登记号）。不从账号名猜测；简称若与现有 `00 LOG` 标题冲突，必须另选。
- `LOG 01`：每个成功新增的来源占一条登记。一个批次可以在同一篇个人日志中连续追加多条登记。
- `LOG 02`：仅记录会影响资料使用的状态、标题、位置或归档变化；普通措辞微调不必记。
- `LOG 03`：记录规则、文件夹和迁移变化；它不是学生答案。
- `LOG 01` 的登记号为 `ZJU-{YYYYMMDD}-{HHMM}-{执行者简称}-{批次序号}`，例如 `ZJU-20260815-1430-xsh-01`。同一批第二份资料使用 `-02`。这避免不同协作者并发时撞号；执行者简称固定使用本人约定的 2–8 个字符。
- `关联资料`一律填写对应的 `ZJU-` 登记号；网页还要保留原始 URL，文件保留原始文件名。

首次建立个人日志后，必须做一次小型验证：追加一条无敏感信息的测试记录，再在共享库中确认更新后的内容或修改时间可见；未验证同步前，日志仅算个人笔记，不能假称已完成共享审计。
